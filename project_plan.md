# Project Plan – Initiative Directory (NocoDB-centric)


## Context

### Goal
Create a public-facing directory of project initiatives with filter/search options, where non-technical team members (managers) can manage the content themselves via NocoDB.

### Scope

**In scope:**
- Self-hosted NocoDB (on Ubuntu server)
- PostgreSQL as main database
- Static frontend generated with 11ty from NocoDB data (read-only for public)
- No separate backend service in production; Nginx serves static files
- Basic monitoring, backups, and secure server setup
- Integrations via Make/Zapier or n8n (for syncing, notifications, etc.)


**Out of scope (for now):**
- User auth in the frontend (only public read)
- Multi-tenant architecture
- Real-time features
- Deep analytics stack

### Users
- Public viewers: visitors of the frontend
- Managers: Team members who have a user account for NocoDB and manage the content.
- Admin: Can make changes to the code.


### Requirements
- Backend / NocoDB:
    - Managers can login to NocoDB and modify the content.
    - Managers can add new databases and properties in NocoDB (without creating issues in the frontend).
        - The frontend reads from specific NocoDB views managed by the admin. Managers can add extra tables/fields; they only affect the frontend if the admin adds them to these views. 
        - The 11ty build uses a fixed set of NocoDB views (e.g. Initiatives_Public, Tags_Public) defined by the admin.
        - Managers can add extra tables/fields in NocoDB; these won’t affect the frontend unless explicitly wired in by the admin.
- Frontend:
    - Static site generated with 11ty at build time.
    - Data from NocoDB is fetched during the 11ty build via REST API (server-to-server using an API token).
    - Public UI is simple, modern, user-friendly, and read-only.
- Admin features:
    - Define data output: there is a simple way for the admin to define which data from NocoDB is being displayed in the frontend (by configuring public views and the 11ty data mapping).
    - Define filter: there is a simple way for the admin to define which properties from NocoDB are being used for filters in the frontend.


## Server & Data 

### Server overview & core stack (summary)

- Ubuntu 24.04 LTS
- Nginx (reverse proxy, TLS)
- Docker & Docker Compose
- PostgreSQL
- UFW + fail2ban
- Certbot / Let’s Encrypt
- Ansible (inventories, group_vars, playbooks)

### High-level architecture

**Components:**

1. **PostgreSQL**
   - Single main database for the directory.
   - Used by NocoDB.

2. **NocoDB**
   - Runs on the existing server.
   - Provides UI for team members to manage initiatives, tags, people, etc.
   - Exposes REST API and public views for data access and integration.

3. **11ty build pipeline**
   - Lives in a separate Git repository.
   - At build time, calls NocoDB REST API (public views only) using an API token.
   - Maps raw NocoDB rows into a stable data structure used by the templates.
   - Generates a fully static site (HTML, CSS, JS).

4. **Frontend**
   - The static files generated by 11ty.
   - Hosted on the Ubuntu server and served by Nginx.
   - Implements filters, search, and navigation client-side (no backend calls in production).

5. **Automation**
   - NocoDB webhooks + Make/Zapier or n8n scenarios (optional).
   - CI pipeline to rebuild the 11ty site:
     - Nightly at 01:00.
     - Manual trigger on demand.


### Environments

- **Production**
	-	Single Ubuntu server (managed shared vCPU).
	-	Existing PostgreSQL 16 instance used by NocoDB and the directory.
	-	Existing NocoDB instance for content editing and views.
	-	11ty-generated static frontend deployed to /var/www/directory and served by Nginx.
	-	Additional services (e.g. n8n) run via Docker/Docker Compose as already configured on the server.
- **Local development**
  - Docker Compose on macOS.
  - Same containers, but local `.env` and demo data.

Optional later:
- **Staging**
  - Same as production but with test data.

### Data model (first draft)

Tables (managed via NocoDB):

1. **initiatives**
   - `id` (uuid / serial)
   - `title` (text)
   - `slug` (text, unique)
   - `short_description` (text)
   - `long_description` (text)
   - `status` (enum: idea / active / paused / finished)
   - `start_date` (date, nullable)
   - `end_date` (date, nullable)
   - `website_url` (text, nullable)
   - `created_at` (timestamp)
   - `updated_at` (timestamp)

2. **tags**
   - `id`
   - `name`
   - `slug`

3. **initiative_tags** (many-to-many join)
   - `id`
   - `initiative_id` (fk → initiatives)
   - `tag_id` (fk → tags)

4. **organizations**
   - `id`
   - `name`
   - `website_url`
   - `country`
   - `city`

5. **people**
   - `id`
   - `name`
   - `email` (internal, not public)
   - `role` (e.g. contact person, project lead)

6. **initiative_people**
   - `id`
   - `initiative_id` (fk → initiatives)
   - `person_id` (fk → people)
   - `role_on_initiative`

You can refine this later once you see how editors use NocoDB.
